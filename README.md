# Мини-CRM «Объекты и задачи» (Строительная компания)

Компактная CRM-система для управления строительными объектами и задачами с ролевым доступом (Постановщик / Исполнитель), конечным автоматом статусов задач (State Machine) и защитой данных на уровне PostgreSQL Row Level Security (RLS).

---

## 1. Стек технологий

* **Frontend**: React 19, TypeScript, Vite, Tailwind CSS v4, Lucide Icons.
* **Backend & Database**: Supabase (PostgreSQL 15+), Supabase Auth, Row Level Security (RLS), PL/pgSQL функции и триггеры.

---

## 2. Быстрый старт

### 2.1. Настройка базы данных (Supabase)
1. Создайте бесплатный проект на [supabase.com](https://supabase.com).
2. Перейдите в левом меню в **SQL Editor** (`>_`).
3. Скопируйте содержимое файла [`supabase/schema.sql`](./supabase/schema.sql), вставьте в редактор и нажмите **Run**.
   * *Скрипт автоматически создаст все таблицы, типы, индексы, RLS-политики, RPC-функцию для смены статусов и триггеры защиты, а также 3 тестовых пользователей и начальные объекты/задачи.*
4. В панели Supabase перейдите в **Authentication** -> **Providers** -> **Email** и снимите галочку **«Enable Signups»** (отключение свободной регистрации согласно ТЗ).

### 2.2. Запуск фронтенда
1. Скопируйте `.env.example` (или создайте `.env.local`):
   ```env
   VITE_SUPABASE_URL=https://your-project.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=your-anon-public-key
   ```
2. Установите зависимости и запустите локальный сервер:
   ```bash
   npm install
   npm run dev
   ```
3. Откройте в браузере `http://localhost:5173`.

## 4. Архитектура безопасности и бизнес-логика

Защита реализована по принципу **Defense-in-Depth (глубокая эшелонированная защита)**:

1. **Разграничение прав (PostgreSQL RLS)**:
   * **Постановщик (`manager`)**: видит все стройки, задачи и историю; может создавать объекты и задачи.
   * **Исполнитель (`worker`)**:
     * Видит только свои задачи (`assignee_id = auth.uid()`).
     * Чужие задачи не возвращаются из базы даже при прямом запросе по ID (`SELECT`).
     * Видит только те объекты (стройки), где у него есть хотя бы одна задача (`EXISTS (SELECT 1 FROM tasks WHERE ...)`).
     * Не может создавать/удалять объекты и задачи.

2. **Защита стейт-машины (State Machine Guard)**:
   * Смена статусов выполняется через защищенную функцию `public.change_task_status(task_id, new_status, comment)`.
   * Функция проверяет матрицу переходов по ТЗ:
     * `new` → `in_progress` (только назначенный исполнитель)
     * `in_progress` → `review` (только назначенный исполнитель)
     * `review` → `accepted` (только руководитель)
     * `review` → `revision` (только руководитель + **обязательный комментарий**)
     * `revision` → `in_progress` (только назначенный исполнитель)
   * **Защита от прямого REST-запроса**: в таблице `tasks` установлен триггер `BEFORE UPDATE`, блокирующий любое прямое изменение поля `status` в обход RPC-функции.

3. **Неизменяемость истории (Audit Log)**:
   * Для таблицы `task_history` закрыты операции `INSERT`, `UPDATE` и `DELETE` для всех пользователей API.
   * Запись в историю формируется автоматически внутри транзакции функции смены статуса (`SECURITY DEFINER`). Подделать, отредактировать или стереть запись истории невозможно.

## 5. Объяснение для руководителя (непрограммиста)

> **Как устроена система и как защищены данные:**
>
> 1. **Два изолированных контура**: Руководитель видит полную картину по всем стройкам компании. Исполнитель (прораб, бригадир) видит **только свои объекты и свои задачи**. Он физически не знает, какие еще объекты ведет компания и какие работы поручены другим исполнителям.
> 2. **Невозможность схитрить в обход приложения**: Безопасность настроена не «кнопками в интерфейсе», а на уровне замков в самой базе данных. Даже если продвинутый пользователь откроет код страницы и попытается через консоль или сторонние программы отправить команду «Я принял свою задачу сам» или «Покажи мне чужие объекты», база данных ответит жестким отказом.
> 3. **Дисциплина статусов**: Исполнитель не может перепрыгнуть через этап проверки сразу в статус «Принята». Руководитель не может вернуть задачу на доработку молча — система обязывает указать, что конкретно нужно исправить.
> 4. **Нестираемый журнал событий (черный ящик)**: Каждое действие фиксируется с точностью до секунды: кто изменил статус, из какого в какой и что написал в комментарии. Ни один сотрудник (и даже руководитель) не может подчистить или подправить эту историю задним числом.

## 6. Принятые решения и допущения

1. **Комментарий при доработке**: ТЗ требует комментарий при переходе `На проверке` -> `На доработке`. В интерфейсе реализовано поле ввода с блокировкой отправки без текста, а в базе данных процедура выбрасывает исключение `RAISE EXCEPTION`, если комментарий пуст или состоит из пробелов.
2. **Удаление объектов и задач**: Право на удаление предоставлено только постановщику (`manager`). При удалении объекта каскадно удаляются его задачи и история.
3. **Открытая регистрация**: Отключена в настройках Supabase Auth. Тестовые пользователи заведены через SQL-миграцию, вход только по выданным учетным записям.
